package / @d402-labs/mpp

@d402-labs/mpp

An MPP (Machine Payments Protocol, the Payment HTTP auth scheme from paymentauth.org / tempoxyz/mpp-specs) scheme for d402 sellers, built on the real mppx SDK (0.13.x).

One 402, three ways to pay:

  • labels: the d402 JSON body, as before (accepts[0], scheme: "d402").
  • stablecoin: an MPP WWW-Authenticate: Payment ... method="tempo" challenge (Tempo charge, testnet by default).
  • card: an MPP WWW-Authenticate: Payment ... method="stripe" challenge (Stripe Shared Payment Token, card), when Stripe is configured and the price is at least Stripe's minimum (USD 0.50; mppx drops the card offer below that).

The agent comes back with either D402-Voucher (d402 path, always wins) or Authorization: Payment (this scheme). The credential is verified and charged through mppx, and the response carries Payment-Receipt.

Seller#

ts
import { createD402 } from "@d402-labs/server";
import { createMppScheme } from "@d402-labs/mpp";

const mpp = createMppScheme({
  amount: "0.007",                                   // USD per request
  realm: "api.example.com",
  tempo: { recipient: process.env.MPP_TEMPO_RECIPIENT }, // testnet by default
  // stripe: { secretKey: process.env.STRIPE_SECRET_KEY }, // card, price >= 0.50
});
const d402 = createD402({ /* ...as usual... */ schemes: [mpp] });
app.route("/", d402.routes);
app.use("/v1/*", d402.gate);

The 402 then looks like:

HTTP/1.1 402 Payment Required
WWW-Authenticate: Payment id="...", realm="api.example.com", method="tempo", intent="charge",
  request="<base64url JSON: amount 7000, currency, recipient, chainId 42431>",
  description="0.007 USD per request", expires="...", opaque="<nonce>"
Content-Type: application/json

{ "d402": "1", "accepts": [ { "scheme": "d402", ... },
  { "scheme": "mpp", "challenge": "WWW-Authenticate", "methods": ["tempo/charge"],
    "amount": "0.007", "currency": "USD", "realm": "api.example.com", ... } ], ... }

The mpp entry in accepts is informational, so JSON-only clients can see MPP is offered. The challenge you pay is the header. tempo.charge() issues one challenge per accepted stablecoin (OUSD, then pathUSD on testnet), so the header may hold more than one Payment ... challenge.

Options

Option Default
amount required Decimal price, e.g. "0.007". Tempo uses 6 decimals, Stripe 2.
currency "USD" Shown in accepts; lowercased for the Stripe charge.
realm request hostname Seller id in the challenge.
methods Tempo + Stripe from the options below Any mppx server methods (tempo.charge(...), stripe.spt(...), Method.toServer(...)).
tempo { recipient: MPP_TEMPO_RECIPIENT, testnet: true } Default Tempo charge. store for a shared replay store across replicas.
stripe on when client / secretKey / STRIPE_SECRET_KEY networkId defaults to STRIPE_NETWORK_ID or "internal".
secretKey MPP_SECRET_KEY, else random per process HMAC key that binds challenge ids. Set it (>= 32 bytes) when you run more than one process or restart often.
verify mppx verifies and charges Replace method verification. Called only after the challenge is checked as ours, unexpired and unspent.
fetch global fetch Used for Tempo RPC calls and Stripe API calls.
description " per request"

Challenges are stateless (HMAC-bound ids, 5 minute expiry from mppx). The scheme also keeps a bounded in-memory set of paid challenge ids, so a credential pays for one request even when a method has no replay store of its own.

Agent#

With the mppx client, which handles the 402 and retries with the credential:

ts
import { privateKeyToAccount } from "viem/accounts";
import { Mppx, tempo } from "mppx/client";

const mppx = Mppx.create({ methods: [tempo({ account: privateKeyToAccount(process.env.KEY as `0x${string}`) })], polyfill: false });
const res = await mppx.fetch("https://api.example.com/v1/quote");
res.headers.get("Payment-Receipt");

Card: stripe.charge({ createToken, paymentMethod }) from mppx/client, where createToken returns a Stripe Shared Payment Token for the challenge's amount, currency and networkId.

From a shell (the mppx CLI; there is no --inspect flag in 0.13, use these):

sh
npx mppx https://api.example.com/v1/quote -v          # pay and fetch, show details
npx mppx sign --dry-run -C "$(curl -s -D - -o /dev/null https://api.example.com/v1/quote \
  | sed -n 's/^www-authenticate: //Ip')"               # parse and validate the challenge only

Charge for real on a laptop#

This container cannot reach Tempo RPCs or Stripe, so nothing below was run here.

Tempo testnet (Moderato, chain 42431, pathUSD):

sh
npx mppx account create --network testnet -a seller   # stored in the OS keychain, autofunded on testnet
npx mppx account create --network testnet -a agent
npx mppx account fund --network testnet -a agent      # more testnet tokens if needed
npx mppx account view -a seller                       # copy the address

export MPP_TEMPO_RECIPIENT=0x...                      # the seller address
export MPP_SECRET_KEY="$(openssl rand -base64 32)"
# start your d402 seller with createMppScheme({ amount: "0.007" })

npx mppx http://localhost:8787/v1/quote -a agent --network testnet -v

Mainnet: tempo: { testnet: false } and a funded mainnet account (--network mainnet).

Stripe card (test mode):

sh
export STRIPE_SECRET_KEY=sk_test_...
export STRIPE_NETWORK_ID=...      # your Stripe network id; mppx's examples use "internal"
# price must be >= 0.50 USD or mppx will not offer the card method

The agent needs a Shared Payment Token from Stripe (createToken above). SPTs are a Stripe preview feature; your account needs access.

What was verified offline, and what needs network#

Verified in this package's tests (src/mpp.test.ts, no network):

  • The 402 carries the mppx-generated challenge beside the d402 body, the body still parses as a d402 Offer, challenges are fresh per request, and mppx's own parser (Challenge.deserializeList, Challenge.verify) and CLI (mppx sign --dry-run) accept them.
  • A Tempo testnet challenge is generated by the real tempo.charge() method (amount in 6-decimal units, chain 42431, recipient).
  • Full handshake with the real mppx client (Mppx.create(...).fetch) against a d402 seller: with a fake method built from Method.from/toClient/toServer, and with the real Stripe client and server methods and a fake Stripe API client (the PaymentIntent request shape is asserted).
  • mppx's real verification path: HMAC check, expiry, tampering, payload schema, method errors mapped to schemeError.
  • A Tempo credential makes mppx query the chain through the injected fetch (eth_getTransactionReceipt); the fake RPC returns nothing, so it fails.

Needs network (not run here): a real Tempo transaction (client signing needs RPC for nonce and fees; the server checks or broadcasts it on chain), and a real Stripe PaymentIntent with a real SPT.
