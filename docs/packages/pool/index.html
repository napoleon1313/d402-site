package / @d402-labs/pool

@d402-labs/pool

The d402 task marketplace. hCaptcha for agents: vendors post labelling work to a pool, any site gates its API with that work instead of its own, and the pool resolves the labels across every site and hands them back to the vendor.

Today a seller needs its own labelled-data need to gate with d402. Most sites do not have one. With a pool, a site with nothing to label still has something to charge agents: the pool's work.

Three roles#

Role Who Key Does
Vendor wants a dataset labelled apiKey posts a batch (labels, instructions, items, some with a known golden answer), exports resolved labels
Site runs a d402-gated API, has no data of its own siteKey leases items, loads them into its own @d402-labs/server, pushes the votes its agents produce
Agent wants API calls its Ed25519 key (never seen by the pool) labels bundles on a site exactly as with any d402 seller

Nothing changes for the agent: the offer, bundle and voucher are plain d402. The site's own d402 server grades the goldens, keeps the agent's trust estimate and mints the vouchers. The pool only aggregates votes.

Trust model (v1)#

  • Sites are trusted parties. A lease carries the golden answers, because the site's d402 server grades them locally; a site that leaks them to its agents only hurts its own grading. Site keys are issued by the pool admin.
  • Agents are not trusted. The pool sees agentHash = sha256(public key), the declared model family, and the vote weight the site's trust estimate assigned (SPEC 5.1/5.2). A duplicate (item, agentHash) is rejected.
  • Resolution is SPEC 5.3 applied across all sites: the top answer needs weight >= 2.0 (resolveWeight), >= 2 distinct agent hashes (resolveMinAgents), and with requireModelFamilies two distinct model families. In practice that is three agreeing agents, which can sit on different sites.
  • Out of scope: money between vendor and site. The pool records a per-site contribution ledger for it: bundlesPassed (bundles the site reported as passed on pool work) and itemsResolvedContributed (resolved items the site voted the winning answer on). GET /v1/sites and GET /v1/stats list it, and GET /v1/ledger breaks it down per site and per batch (see Ledger and statements).

v1 simplifications, documented so nobody is surprised:

  • A lease serves one batch at a time: the open batch with the most leasable items for that site, so the labels and instructions in a lease are uniform and a site can build its d402 server from them. Every lease item still carries batchId, labels and instructions.
  • A site serves one label set. Its sync skips a lease whose labels differ from the site's (and logs it). Run one site per label set.
  • Goldens are sent at roughly 25% of a lease and are not consumed; they can repeat across leases (the site ignores items it already has).
  • Pool item ids are :; the site prefixes them pool: locally so they never collide with its own items. Exports use the vendor's id.

Site with no data of its own, in 10 lines#

sh
d402-pool serve --port 8795 --admin-token $POOL_ADMIN --db pool.db
d402-pool vendor create "Acme Data" --admin-token $POOL_ADMIN           # -> { vendorId, apiKey }
d402-pool site create news.example news.example --admin-token $POOL_ADMIN   # -> { siteId, siteKey }
d402-pool batch create --vendor-key $VENDOR_KEY --jsonl tickets.jsonl --labels low,medium,high,critical --name "tickets"
d402-proxy --upstream https://api.news.example --scope /v1 --pool-url http://localhost:8795 --site-key $SITE_KEY
# agents hit https://.../v1, get a 402, label pool tickets, call through
d402-pool batch status $BATCH_ID --vendor-key $VENDOR_KEY
d402-pool batch export $BATCH_ID --vendor-key $VENDOR_KEY > labels.jsonl
d402-pool stats --admin-token $POOL_ADMIN                                 # the contribution ledger

d402-mcp-seller --pool-url ... --site-key ... does the same for a seller that is an MCP server.

Two things that surprise people on a first run:

  • Votes reach the pool on the site's sync interval (15 s by default), not when the agent submits. batch status right after agents earn shows votes: 0; wait for the next sync.

  • Agents see item ids as pool::, not your vendor ids. An answers file keyed by vendor ids (for a demo agent or d402 earn --answers) must be re-keyed first:

    sh
    jq --arg b "$BATCH_ID" 'with_entries(.key = "pool:\($b):\(.key)")' answers.json > pool-answers.json
# or: node -e 'const [f,b]=process.argv.slice(1);const a=require(require("path").resolve(f));console.log(JSON.stringify(Object.fromEntries(Object.entries(a).map(([k,v])=>["pool:"+b+":"+k,v]))))' answers.json "$BATCH_ID" > pool-answers.json

API#

All JSON. Auth is Authorization: Bearer ; a missing, wrong or wrong-type key is 401 { error: "unauthorized" }.

Route Key Body / query Returns
GET /health none { ok, now }
POST /v1/vendors admin { name } 201 { vendorId, apiKey } (the key is shown once; only its sha256 is stored)
POST /v1/sites admin { name, sellerId } 201 { siteId, siteKey }
GET /v1/sites admin { sites: [{ id, name, sellerId, created, bundlesPassed, itemsResolvedContributed, votes }] }
GET /v1/stats admin { totals, vendors[], sites[], batches[], now }
POST /v1/batches vendor { name, instructions?, labels[], items: [{ id, text, golden? }] } 201 { batchId, items, goldens }. 400 with bad_labels (fewer than 2), no_goldens (goldens are what make the labels trustworthy), bad_golden (not one of the labels), bad_items
GET /v1/batches/:id vendor { id, name, status, labels, instructions, total, goldens, unknown, resolved, open, leased, votes, agreementRate }
GET /v1/batches/:id/export vendor JSONL, one { id, text, answer, weight, voters, sites } per resolved item
POST /v1/batches/:id/close vendor { batchId, status: "closed" }; no new leases from it
POST /v1/lease site { count, exclude?: string[] } { items: [{ id, text, golden?, batchId, instructions, labels }], expiresAt }
POST /v1/votes site { votes: [{ itemId, answer, weight, agentHash, model? }], passedBundles?, passedBundlesByBatch?: { [batchId]: n }, held?: string[] } { accepted, rejected: [{ itemId, agentHash, reason }], resolved: [{ itemId, answer }] }
POST /v1/webhooks site { url, events: ["batch.created" | "batch.low" | "batch.closed"], secret? } 201 { webhookId, id, url, events, signed, created }. 400 bad_url, bad_events; 409 too_many_webhooks (20 per site)
GET /v1/webhooks site { webhooks: [{ id, url, events, signed, created }] } (never the secret)
DELETE /v1/webhooks/:id site { webhookId, deleted: true }; 404 unknown_webhook for another site's id
GET /v1/webhooks/:id/deliveries site ?limit=50 { webhookId, deliveries: [{ id, event, status, attempts, lastError, httpStatus, at, updated }] }, newest first
POST /v1/referrals site { referrerHash, refereeHash } 201 { referrerHash, refereeHash, status: "pending" }. 400 bad_agent_hash, self_referral; 409 already_referred, referee_active, referrer_inactive
GET /v1/agents/:hash/credits site or admin { agentHash, earned, redeemed, balance, referredBy, referrals: { pending, credited }, events[] }
POST /v1/agents/:hash/credits/redeem site { calls } { agentHash, redeemed, balance }; 409 insufficient_credits
GET /v1/ledger admin ?site=&batch=, Accept: text/csv or ?format=csv { rows: LedgerRow[], now } or CSV
GET /v1/sites/:id/ledger site (own id or me) ?batch=, CSV as above the site's own rows
GET /v1/vendors/:id/statement vendor (own id or me) ?batch=, CSV as above { vendorId, vendorName, batches: StatementRow[], totals, now }

POST /v1/batches also takes an optional unitPrice (non-negative number, default 0) for the statement's cost basis.

agreementRate is, over resolved items, the share of votes that agree with the resolved answer.

Lease rules: open batches only; unknown items with the fewest votes first; never an item currently leased to the same site, already resolved, or in exclude; roughly 25% goldens. A lease expires after leaseTtl (default 1h) and its items become leasable again by the same site; votes on an expired lease still count, because a site may keep an item open longer than the lease.

Vote rejection reasons: unknown_item, golden, resolved, bad_label, bad_weight (needs 0 < weight <= 1), bad_agent_hash (64 hex chars), not_leased, duplicate. held is the list of pool item ids the site still has open; any of them already resolved by other sites' votes come back in resolved, so the site can stop handing them out.

Work-available webhooks#

Sites, and the agents behind them, want to earn during idle time: when a vendor posts a batch, a site whose local pool is empty should lease it now, not on its next 15 s interval (or hours later, if the interval is long).

A site registers a URL with its site key:

sh
d402-pool webhook create --site-key $SITE_KEY --url https://api.news.example/d402/pool-webhook \
  --events batch.created,batch.low,batch.closed --secret $WEBHOOK_SECRET   # -> { webhookId, ... }
d402-pool webhook list --site-key $SITE_KEY
d402-pool webhook deliveries $WEBHOOK_ID --site-key $SITE_KEY            # the delivery log
d402-pool webhook delete $WEBHOOK_ID --site-key $SITE_KEY

Events are pool-wide: every webhook subscribed to an event gets it, whichever site registered it.

Event When data
batch.created a vendor posted a batch { batchId, name, labels, instructions, total, goldens }
batch.low open unknown items of an open batch dropped below 20% of its unknown items; once per batch { batchId, name, labels, unknown, open, resolved }
batch.closed the vendor closed the batch; once { batchId, name, total, resolved, open }

Delivery, exactly:

  • POST with Content-Type: application/json and the body { "event": "", "at": , "data": { ... } }.
  • Headers X-D402-Event: and X-D402-Delivery: .
  • When the webhook has a secret: X-D402-Signature: sha256=, the HMAC-SHA256 of the raw body bytes with the secret as key. Verify it on the raw body before parsing, with a constant-time compare (verifyWebhookSignature(secret, rawBody, header) does this). Reject a payload whose at is far from your clock to limit replays (the listener below allows 300 s).
  • Each attempt times out after 5 s. Any non-2xx answer, network error or timeout is retried: 3 attempts in all, 1 s then 4 s apart. The same body and signature are sent on every attempt, so a receiver can dedupe on X-D402-Delivery.
  • Every delivery is logged in webhook_deliveries (webhook id, event, status pending|retrying|delivered|failed|cancelled, attempts, last error, last HTTP status, emitted at, last attempt at). Deleting a webhook deletes its log and cancels its pending retries.

The secret is stored as given (the pool must sign with it) and is never returned by the API.

Site side, startWebhookListener mounts the receiving route and turns an event into an immediate sync:

ts
import { createPoolSync, startWebhookListener } from "@d402-labs/pool";

const sync = createPoolSync({
  d402, poolUrl, siteKey,
  onWorkAvailable: ({ leased, batchId }) => console.log(`leased ${leased} from ${batchId}`),
});
sync.start();
// on the site's own Hono app: POST /d402/pool-webhook
startWebhookListener({ app, secret: process.env.WEBHOOK_SECRET!, sync, onEvent: (evt, result) => {} });
// or on its own port
const l = startWebhookListener({ port: 8796, secret, sync });
await l.ready; // { port }

The listener answers 401 bad_signature, 400 bad_request (unknown event, not JSON) or 400 stale (at more than toleranceSec, default 300, from its clock); otherwise 202 at once, then runs sync.wake() and calls onEvent(payload, syncResult). wake() is syncOnce() except that when a sync is already running it waits for it and runs one more, so an event that lands mid-sync is not lost. A sync leases only when the site is under its low-water mark, so a busy site ignores batch.created until it needs work. onWorkAvailable is called whenever a lease loads new items, from any trigger.

Not done: d402-proxy and d402-mcp-seller do not mount the listener yet; a site using them still relies on the interval. Agents cannot register webhooks; only sites can, with their site key. The pool posts to any http(s) URL a site gives it, private addresses included: fine with trusted sites, not for an open pool.

Referral credits#

A site, or the pool operator, rewards agents that bring other agents. Pool-level, no spec change:

  1. The site registers POST /v1/referrals { referrerHash, refereeHash } with its site key. Hashes are sha256(agent public key), the same agentHash the site already sends with votes (hashAgentKey(publicKey)).
  2. Recorded once per referee. Refused when the referee already has accepted votes in the pool (referee_active: a referral must come first), when the referrer has none (referrer_inactive: only agents that have done pool work can refer), and for self-referral.
  3. When a push to POST /v1/votes contains the referee's first accepted votes, the pool credits referralBonus (default 5) to both referrer and referee, once. Rejected votes do not count.
  4. GET /v1/agents/:hash/credits (site key or admin) shows earned, redeemed, balance, who referred the agent, its referrals, and the credit event log. POST /v1/agents/:hash/credits/redeem { calls } debits the balance atomically and records which site redeemed.

Turning credits into API calls is the site's job, and here is the limit: @d402-labs/server has no public API to add calls to an existing voucher or to mint a voucher outside a passed bundle, and this change does not touch the server. So the site-side helper does not mint:

ts
import { applyReferralCredits, createPoolClient } from "@d402-labs/pool";
const client = createPoolClient({ poolUrl, key: siteKey });
await applyReferralCredits({ client, publicKey });           // { agentHash, balance, applied: 0 }: reports only
await applyReferralCredits({ client, publicKey, grant: async (calls, agentHash) => {
  myAllowance.add(agentHash, calls);                          // the site's own mechanism
} });                                                          // redeems at the pool, then grants

With grant it redeems first, then grants, so two sites cannot both spend the same credits; if grant throws, the result carries grantError and the credits stay redeemed (the redeem is in the agent's credit events for a manual fix). Minting d402 vouchers from credits needs a server API such as grantCalls(jti, n) and is left to a follow-up.

Abuse limits, stated plainly: an agent with two keys can refer itself once it has done some pool work; the pool cannot tell two keys of one operator apart. The bonus is per referee and needs real accepted votes, which bounds it, and sites are trusted parties that can choose not to register referrals.

Ledger and statements#

No money moves through the pool. The ledger is the record a payout between vendors and sites would be computed from; the statement is what a vendor would be invoiced against. Both are read-only views over the votes and bundle reports.

GET /v1/ledger (admin, ?site=, ?batch=) and GET /v1/sites/:id/ledger (site key, own rows only; me works) return one row per site and batch the site worked on:

Column Meaning
bundlesPassed bundles the site reported as passed that touched this batch. The sync sends passedBundlesByBatch; a bundle with items from two batches counts once in each. A push without the breakdown (an older site) is booked to the batch with the most accepted votes in that push
itemsResolvedContributed resolved items of the batch the site voted the winning answer on
votesAccepted the site's accepted votes on the batch
firstActivity, lastActivity unix seconds of the site's first and last vote or bundle report on the batch
batchResolved resolved items in the batch
share itemsResolvedContributed / batchResolved. When two sites voted the winner on one item both are credited, so shares of a batch can sum above 1
weightedShare per resolved item, the site's weight on the winning answer / the item's winning weight, summed, then / batchResolved. Sums to 1 across sites; the better basis for splitting a fixed amount

GET /v1/vendors/:id/statement (vendor key, own id or me, ?batch=) returns per batch: total, goldens, unknown, resolved, open, votes, agreementRate, sites (sites with accepted votes), unitPrice (from batch create, default 0) and costBasis = resolved * unitPrice, plus totals. unitPrice has no currency: it is whatever vendor and pool operator agree on, and nothing is charged.

Both answer CSV (RFC 4180, header row, CRLF) with Accept: text/csv or ?format=csv.

sh
d402-pool ledger --admin-token $POOL_ADMIN [--site <id>] [--batch <id>] [--csv]
d402-pool ledger --site-key $SITE_KEY [--csv]                       # a site's own rows
d402-pool statement --vendor-key $VENDOR_KEY [--batch <id>] [--csv]

Library#

ts
import { createPool, createPoolSync, createPoolClient } from "@d402-labs/pool";

// the pool
const pool = createPool({ db: "pool.db", adminToken: process.env.POOL_ADMIN! });
serve({ fetch: pool.app.fetch, port: 8795 });
// pool.vendors.create(name), pool.sites.create(name, sellerId), pool.batches.create(vendorId, input),
// pool.batches.status(id) / export(id) / close(id), pool.lease(siteId, count), pool.votes(siteId, input), pool.stats()
// pool.webhooks.create/list/delete/deliveries(siteId, ...), pool.webhooks.idle()
// pool.referrals.create(siteId, input) / credits(hash) / redeem(siteId, hash, calls)
// pool.ledger({ siteId?, batchId? }), pool.statement(vendorId, batchId?)

// a site: its own d402 server plus the sync
const d402 = createD402({ ...labelsFromTheFirstLease });
const sync = createPoolSync({ d402, poolUrl, siteKey, lowWater: 40, leaseSize: 200, intervalMs: 15_000 });
sync.start();                       // lease when low, push votes, mark resolved; errors are logged and retried
await sync.syncOnce();              // { leased, pushedVotes, resolved, error? }
await sync.wake();                  // sync now, or right after the one in flight
await sync.leaseNow();              // one lease regardless of the mark: { leased, labels, instructions }
sync.stats;                         // { syncs, leased, pushedVotes, rejectedVotes, passedBundles, resolved, errors, lastLease }

createPool options: db, adminToken, now, resolveWeight (2.0), resolveMinAgents (2), requireModelFamilies (false), leaseTtl (3600), goldenRatio (0.25), referralBonus (5), webhooks: { fetch, sleep, timeoutMs (5000), backoffMs ([1000, 4000]), log }. createPoolSync leases when fewer than lowWater unknown items are left that no local agent has answered yet (or when no live goldens remain), pushes d402.store.answersSince(cursor) with agent keys hashed, derives passedBundles from the distinct bundle ids among the pushed pool votes (and per batch, as passedBundlesByBatch), and keeps the cursor in the server's pool_sync table so a restart does not re-push. fetch, log and onWorkAvailable are injectable.

CLI#

d402-pool serve [--port 8795] [--db pool.db] [--admin-token T] [--lease-ttl 3600] [--require-model-families] [--referral-bonus 5]
d402-pool vendor create <name>                      admin
d402-pool site create <name> <sellerId>             admin
d402-pool stats                                     admin
d402-pool batch create --vendor-key K --file batch.json
d402-pool batch create --vendor-key K --jsonl items.jsonl --labels a,b --name N [--instructions "..."]
d402-pool batch status|export|close <id> --vendor-key K
d402-pool ledger [--site <id>] [--batch <id>] [--csv]   admin, or --site-key K for the own rows
d402-pool statement --vendor-key K [--batch <id>] [--csv]
d402-pool webhook create --site-key K --url U --events batch.created,batch.low,batch.closed [--secret S]
d402-pool webhook list|delete <id>|deliveries <id> --site-key K
d402-pool credits <agentHash> --site-key K          (or --admin-token)
d402-pool referral create <referrerHash> <refereeHash> --site-key K

--pool-url (default http://localhost:8795, env D402_POOL_URL), --admin-token (env D402_POOL_ADMIN_TOKEN), --vendor-key (env D402_POOL_VENDOR_KEY), --site-key (env D402_POOL_SITE_KEY). serve without an admin token generates one and prints it.

Tests#

packages/pool/src/*.test.ts: the pool over app.request (auth, batch validation, lease rules with an injected clock, votes, cross-site resolution, contribution ledger, export accuracy with simulated agents), the sync against a real createD402 and a real pool in one process, and the CLI spawned with serve --port 0. webhooks.test.ts: registration and auth, each event's payload and signature, once-only batch.low and batch.closed, retries with the 1 s / 4 s backoff (injected sleep), timeout, the delivery log, the listener's signature / replay checks, and pool -> webhook -> site lease end to end (in process with the interval never firing, and over real HTTP on a port). referrals.test.ts: validation, crediting once on the first accepted votes, redeem, applyReferralCredits, and a referral through a real site and its sync. ledger.test.ts: per-site per-batch rows and shares on a hand-computed scenario, filters, CSV, the vendor statement, and opening a database from before the new columns. The proxy's pool mode is tested in packages/proxy/src/pool.test.ts, including one spawned d402-proxy against a real pool and a fake upstream.
