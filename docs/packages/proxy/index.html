package / @d402-labs/proxy

@d402-labs/proxy

Put a d402 gate in front of any existing HTTP API with one command. No code on the seller side: the proxy sits between agents and your API, answers 402 Payment Required with a d402 offer, hands out classify bundles, grades them, and forwards paid requests to your API unchanged.

sh
npx -p @d402-labs/proxy d402-proxy --upstream https://api.example.com --tasks ./tasks.jsonl --labels sports,business,tech,world

Use npx -p @d402-labs/proxy d402-proxy, not npx d402-proxy: the unscoped name is not ours on npm, and anyone could publish it. The package is not on npm yet; until it is, run node packages/proxy/dist/cli.js after pnpm build in a clone.

Put d402 in front of your API in 60 seconds#

  1. Write a JSONL task file: one {"id","type":"classify","text"} per line, some with a "golden" label (SPEC 10). To try the proxy first, use the sample that ships with the package: --tasks node_modules/@d402-labs/proxy/examples/tasks.sample.jsonl after npm i @d402-labs/proxy, or packages/proxy/examples/tasks.sample.jsonl in a clone (60 headlines, labels sports,business,tech,world, 20 golden). Item ids and texts are shown to agents. Use random ids; never encode golden/unknown in the id or the text.
  2. export D402_SECRET=$(openssl rand -hex 32)
  3. npx -p @d402-labs/proxy d402-proxy --upstream https://api.example.com --tasks ./tasks.jsonl --labels a,b,c --public-url https://d402.example.com
  4. Point agents (or your DNS) at the proxy instead of the API, and make sure they cannot reach the API itself (next section). curl -i https://d402.example.com/anything now returns a 402 with the offer.
  5. Agents label bundles, earn vouchers and call through. Resolved labels: curl -H 'Authorization: Bearer $TOKEN' https://d402.example.com/.well-known/d402/admin/export (with --admin-token $TOKEN).

Without --public-url the offer's taskUrl is http://localhost:, and the proxy warns at boot: --public-url not given; taskUrl is http://localhost:, which remote agents cannot reach. Behind a reverse proxy that sets X-Forwarded-Host and X-Forwarded-Proto, --trust-proxy builds taskUrl from those headers per request instead. --public-url is still the better choice, because sellerId (the voucher issuer) defaults to its host and should not change between requests.

Where tasks come from

The task file is the labelling work agents pay with. It can be your own data (rows you want labelled, plus a few dozen you already know the answer to as goldens), work leased from a d402 pool (--pool-url, below), or the sample above to see the flow end to end. No public pool is hosted yet: --pool-url needs a pool you or a partner runs (@d402-labs/pool).

Each tier needs enough goldens: a bundle for a new agent holds max(1, round(items * 0.4)) of them, so the default tiers need 2, 10 and 20. At boot the proxy warns tier needs >= N goldens for new agents, pool has M for each tier it cannot serve; with --strict-tiers it leaves those tiers out of the offer instead (and refuses to start if none is left).

The proxy is only a gate if agents cannot reach the upstream directly#

The proxy forwards to --upstream; it cannot stop anyone from calling that URL themselves. The offer never names the upstream (sellerId defaults to the host of --public-url), but the upstream must still refuse traffic that did not come through the proxy. Two ways:

  1. Private network. Run the upstream where only the proxy can reach it: bound to 127.0.0.1, a private subnet or a container network, with no public address or DNS name.

  2. A shared header. Give the proxy a secret header that it adds to every forwarded request, and have the upstream reject requests without it:

    sh
    export D402_PROXY_SECRET=$(openssl rand -hex 32)
d402-proxy --upstream https://api-origin.example.com --tasks ./tasks.jsonl \
  --public-url https://api.example.com --upstream-header "X-D402-Proxy: $D402_PROXY_SECRET"
    js
    // in the upstream, before any route
app.use((req, res, next) =>
  req.get("X-D402-Proxy") === process.env.D402_PROXY_SECRET ? next() : res.status(403).end());

    The proxy sets the header after copying the client's headers, so a client cannot supply its own value. --upstream-header is repeatable. Use TLS to the upstream when the header crosses a network you do not control.

What it does#

  • Mounts the d402 routes: GET /.well-known/d402 (the offer), GET /.well-known/d402/tasks?tier=, POST /.well-known/d402/tasks/:bundleId.
  • Runs d402.gate on every request whose path starts with a --scope prefix (default: everything except /.well-known/* and --open paths). No valid voucher means 402 with the offer; a valid one is decremented and the request goes through with D402-Calls-Remaining on the response.
  • Forwards every request, gated or open, to --upstream: same method, path, query, headers and body (streamed). Hop-by-hop headers and D402-Voucher are dropped, Host becomes the upstream host, and X-Forwarded-For, X-Forwarded-Proto, X-Forwarded-Host, Via and every --upstream-header are added. The upstream status, headers and body come back unchanged except for hop-by-hop headers.
  • Logs one line per request to stderr: GET /v1/items 200 12ms paid (paid, open or 402).
  • Keeps the pool, agents and vouchers in SQLite (--db), in memory by default.

Flags#

Flag Default Meaning
--upstream required base URL of the API to gate; a path prefix is kept (https://x/base + /v1 -> https://x/base/v1)
--tasks none classify task file loaded at boot (SPEC 10)
--scope / path prefixes to gate; also the voucher scope in the offer
--labels derived classify labels, at least 2; when absent the distinct golden values of the task file are used (a warning says so)
--seller-id host of --public-url sellerId in the offer and iss of vouchers (never the upstream host, which would tell agents where to go around the gate)
--public-url http://localhost: public base URL of the proxy; taskUrl is /.well-known/d402/tasks. Without it the proxy warns that remote agents cannot reach taskUrl
--trust-proxy off without --public-url: build taskUrl per request from X-Forwarded-Host / X-Forwarded-Proto. Only behind a reverse proxy that sets them
--upstream-header "Name: value" none added to every forwarded request, overriding a client-sent header of the same name; repeatable. See "The proxy is only a gate..." above
--secret env D402_SECRET voucher HMAC secret; with neither, a random one is generated and a warning says vouchers will not survive a restart
--port 8787 listen port (0 picks a free one and prints it)
--tier s:5:1000:10 m:25:5000:60 l:50:10000:150 a tier; repeat the flag for several
--strict-tiers off leave out of the offer every tier the pool has too few goldens for (max(1, round(items * 0.4)) per bundle for a new agent); without it the proxy only warns
--db in memory SQLite path
--bind-vouchers off SPEC 7.1: spends must carry D402-Key, D402-Timestamp, D402-Sig
--require-spend-nonce off with --bind-vouchers: bound spends must also carry a fresh D402-Nonce (SPEC 7.2), so a captured spend cannot be replayed
--require-model-families off an item resolves only with votes from 2 distinct D402-Model families
--x402-pay-to <0x..> off also accept USDC over x402: every 402 gets x402Version and an exact entry paying this address. Needs @d402-labs/x402 installed
--x402-price $0.007 x402 price per request
--x402-network base-sepolia x402 network (EVM networks of the x402 v1 SDK)
--x402-facilitator https://x402.org/facilitator x402 facilitator that verifies and settles payments
--mpp-tempo-recipient <0x..> off also accept MPP: every 402 gets a WWW-Authenticate: Payment challenge for a Tempo stablecoin charge to this address. Needs @d402-labs/mpp installed
--mpp-amount 0.007 MPP amount per request
--mpp-stripe-key off adds a Stripe card method to the MPP challenge (on its own it turns MPP on too); MPP_SECRET_KEY and STRIPE_SECRET_KEY from @d402-labs/mpp apply as well
--admin-token off enables the admin endpoints below
--open none path prefixes that are never gated, e.g. /health,/docs
--instructions SPEC default instructions shown in every bundle
--pool-url none a @d402-labs/pool to lease labelling work from, for a site with no data of its own; see below
--site-key env D402_SITE_KEY site key issued by the pool admin
--config none JSON config file, see below
-h, --help usage

Prefix matching is the same rule the server uses for voucher scope: --scope /v1 gates /v1, /v1/items and /v1x.

Paths are normalised before the gate looks at them, and the upstream receives the normalised path: repeated slashes are collapsed and ./.. segments resolved (//v1/items and /x/../v1/items both become /v1/items); percent-encoding is kept as sent. A path that still looks odd (a backslash, NUL, or an encoded /, \, . or NUL such as /v1%2Fitems) is always gated and forwarded as sent. Matching is case-sensitive, so /V1/items is outside --scope /v1: if your upstream treats paths case-insensitively, gate with --scope / (and --open for the free paths).

Every payment option, zero code

sh
d402-proxy --upstream https://api.example.com --tasks ./tasks.jsonl --scope /v1 --open /health \
  --bind-vouchers --require-spend-nonce --require-model-families \
  --x402-pay-to 0xYourUsdcAddress --x402-price '$0.007' \
  --mpp-tempo-recipient 0xYourTempoAddress --mpp-amount 0.007

One 402 then offers labels (d402), USDC (x402 exact) and MPP (WWW-Authenticate: Payment). A D402-Voucher always takes the d402 path; otherwise an X-PAYMENT or Authorization: Payment credential is verified by its scheme.

@d402-labs/x402 and @d402-labs/mpp are optional dependencies: they pull in the x402 and MPP SDKs, which are most of the install size. The proxy imports them only when an --x402-* or --mpp-* flag is set. If your package manager skipped them (npm i --omit=optional), install the one you need: npm i @d402-labs/x402 or npm i @d402-labs/mpp. Without it the proxy exits with code 2 and install @d402-labs/x402 to use --x402-pay-to (or the MPP equivalent).

A site with no data of its own#

With --pool-url and --site-key and no --tasks/--labels, the proxy leases its first batch of work from the pool at boot, builds the d402 server with that lease's labels and instructions, and keeps syncing: it leases more when it runs low, pushes the votes its agents produce (agent keys hashed), and marks items the pool resolved. Boot fails if the pool is unreachable or has no open work, because there would be no label set to serve an offer with.

sh
d402-proxy --upstream https://api.example.com --scope /v1 --pool-url https://pool.example.com --site-key $SITE_KEY

The boot line reads pool: 200 items (50 golden) leased from https://pool.example.com. --tasks/--labels still win when given; the sync then only loads leases whose labels match. See @d402-labs/pool.

Config file#

The same keys in camelCase. Flags override the file; the file overrides env D402_SECRET. tiers entries may be "id:items:est_tokens:calls" strings or SPEC 3 tier objects; scope, labels and open may be arrays or comma lists.

json
{
  "upstream": "https://api.example.com",
  "tasks": "./tasks.jsonl",
  "scope": ["/v1"],
  "labels": ["sports", "business", "tech", "world"],
  "sellerId": "d402.example.com",
  "publicUrl": "https://d402.example.com",
  "trustProxy": false,
  "upstreamHeaders": ["X-D402-Proxy: change-me"],
  "port": 8787,
  "tiers": ["s:5:1000:10", { "id": "m", "items": 25, "est_tokens": 5000, "reward": { "calls": 60 } }],
  "strictTiers": false,
  "db": "./d402.db",
  "bindVouchers": false,
  "requireSpendNonce": false,
  "requireModelFamilies": false,
  "x402PayTo": "0x...",
  "x402Price": "$0.007",
  "mppTempoRecipient": "0x...",
  "mppAmount": "0.007",
  "adminToken": "change-me",
  "open": ["/health", "/docs"],
  "poolUrl": "https://pool.example.com",
  "siteKey": "..."
}
sh
d402-proxy --config d402.json --port 9000

Admin endpoints#

Only mounted when --admin-token is set. Both need Authorization: Bearer ; anything else is 401.

Endpoint Returns
GET /.well-known/d402/admin/stats { stats, agents, resolved }: pool stats (tasks.stats()), every agent with its accuracy and block state (agents.list()), and the count of resolved items
GET /.well-known/d402/admin/export the resolved unknown items as JSONL (application/x-ndjson), one { id, text, answer, weight, voters } per line
sh
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8787/.well-known/d402/admin/stats | jq
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8787/.well-known/d402/admin/export > resolved.jsonl

As a library#

ts
import { serve } from "@hono/node-server";
import { createProxyApp, parseArgs } from "@d402-labs/proxy";

const { app, d402 } = createProxyApp({
  upstream: "https://api.example.com",
  tasks: "./tasks.jsonl",
  labels: ["sports", "business", "tech", "world"],
  scope: ["/v1"],
  open: ["/health"],
  publicUrl: "https://d402.example.com",
  secret: process.env.D402_SECRET,
});
serve({ fetch: app.fetch, port: 8787 });
// d402.tasks.stats(), d402.agents.list(), d402.tasks.exportResolved(), d402.close()

createProxyApp(opts) is pure apart from opening the SQLite store, so it can be driven with app.request() in tests; log, warn and fetch are injectable. It is synchronous and does not import the optional payment packages, so it throws on x402PayTo / mppTempoRecipient / mppStripeKey; use buildProxyApp for those. buildProxyApp(opts) is what the CLI runs: it imports @d402-labs/x402 / @d402-labs/mpp when their options are set, then does the same plus the pool boot path (poolUrl, siteKey, injectable poolFetch), returning { app, d402, sync? }. parseArgs(argv, env?) turns CLI flags into the same options object.

Notes#

  • The proxy decodes compressed upstream bodies (fetch does), so Content-Encoding and Content-Length are dropped from such responses; everything else passes through.
  • X-Forwarded-For is appended to when the request already carries one. The server's per-IP rate limit reads the first entry.
  • The proxy needs Node 22+ for node:sqlite. The CLI hides the node:sqlite ExperimentalWarning; other warnings still print.
