client / curl

d402 with curl

walkthrough.sh runs the whole protocol from spec/SPEC.md against the example seller (examples/search-proxy) using only curl for HTTP. The one thing curl cannot do, the Ed25519 signature over the answers, is done with the Python client in clients/python (stdlib + cryptography); no TypeScript toolchain is needed on the agent side. jq is used for pretty printing when installed, otherwise python3.

sh
bash clients/curl/walkthrough.sh      # from the repo root; needs node + node_modules for the seller

The script starts the seller on a free port in the background, walks through steps 1-7 below, and stops it on exit.

What happens#

Step Spec Request What you get
1 3 GET /search?q=... with no voucher 402 with the offer: taskUrl, scope, tiers (same body at /.well-known/d402)
2 2 generate an Ed25519 keypair D402-Key is the base64url public key
3 4 GET {taskUrl}?tier=s + D402-Key a bundle: 5 items to label; some are hidden goldens
4 8 label every item {itemId: label} (the demo reads answer-key.json; a real agent asks an LLM)
5 5 POST {taskUrl}/{bundleId} with {answers, model, sig} 200 with the voucher (an HS256 JWT) and calls, or 422 quality
6 7 GET /search?q=... + D402-Voucher 200, D402-Calls-Remaining counts down
7 7.1, 7.2 the same with D402-Key, D402-Timestamp, D402-Nonce, D402-Sig what a seller with bindVouchers (+ requireSpendNonce) requires

The signed strings are exactly:

"d402:submit\n" + bundleId + "\n" + canonicalJSON(answers)                       # step 5
"d402:spend\n"  + METHOD + "\n" + path + "\n" + jti + "\n" + timestamp [+ "\n" + nonce]   # step 7 (nonce: SPEC 7.2)

canonicalJSON is JSON with keys sorted recursively and no whitespace; in Python that is json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False).

Notes on the output:

  • Step 1's 402 carries "error": "missing_voucher" on top of the offer. After a voucher runs out, the same route answers 402 with "error": "voucher_exhausted", which is how an agent knows to earn again.
  • Step 3: the bundle is tier s (5 items). With a fresh key the golden ratio is 0.4, so 2 of the 5 are controls and both must be right (c / g >= 0.8). The seller never says which.
  • Step 5: the printed signed message is the exact byte string the signature covers; note the answers are re-serialised with sorted keys even though answers.json was not sorted.
  • Step 6: each spend decrements the counter stored server-side under the voucher's jti; the JWT itself never changes.
  • Step 7: the example seller does not bind vouchers, so it serves the request without checking the extra headers. With bindVouchers: true a missing key, stale timestamp or bad signature gets 402 bad_key / stale_timestamp / bad_signature, and re-sending the same nonce gets 402 replayed_spend (the Python test suite covers this against a binding seller).
