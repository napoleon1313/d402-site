d402

quick startread the specpackagesuse cases

Pay for API access with labelled data instead of micropayments.

d402 ("data 402") is an HTTP payment scheme for agents. A gated route returns 402 Payment Required with an offer. Instead of sending USDC, the agent labels a bundle of items, passes hidden control items, and gets a voucher worth N calls. The seller gets labelled data. The agent needs no wallet.

Reviewing this for the hackathon? SUBMISSION.md maps every piece to the sponsor tracks with its honest limits, and OVERVIEW.md has the full design.

It is reCAPTCHA for agents:

reCAPTCHA d402
Gate a page Gate an API route
Type 2 words Label a bundle of 5 to 50 items
One word is known, one is unknown Some items are golden (known), the rest are votes
Humans pay in seconds Agents pay in tokens
Google got digitized books The seller gets a labelled dataset

The offer uses the same accepts array shape as x402, so a seller can list USDC and d402 side by side and the agent picks.

Packages#

Package What it is
spec/SPEC.md The protocol. Read this first.
@d402-labs/spec Zod schemas, header names, defaults, Ed25519 signing helpers.
@d402-labs/server Hono middleware for sellers: offer, bundles, grading, trust, vouchers. SQLite via node:sqlite. CLI d402-tasks.
@d402-labs/client Fetch wrapper for agents: earns on 402, caches vouchers, retries. Pluggable solver. CLI d402-agent.
@d402-labs/mcp MCP server so an LLM agent is its own solver: d402_get_bundle, d402_submit, d402_fetch, d402_status, d402_discover.
@d402-labs/proxy d402-proxy: put a d402 gate in front of any existing API with one command. No code.
@d402-labs/mcp-seller d402-mcp-seller: the seller as a remote MCP server (Streamable HTTP). Tools paid for in labelled data; one voucher works on HTTP routes and MCP tools; session or key identity; --tools-module for your own gated tools.
@d402-labs/x402 x402 as a second scheme on the same gate: the 402 also lists an x402 exact USDC entry, and an X-PAYMENT header is verified and settled through a facilitator.
@d402-labs/mpp MPP (the Payment HTTP auth scheme) as a third scheme, on the mppx SDK: a WWW-Authenticate: Payment challenge for Tempo stablecoin or Stripe card.
@d402-labs/pool d402-pool: the task marketplace. Vendors post labelling work, any site gates its API with it (d402-proxy --pool-url), the pool resolves labels across sites and keeps a per-site contribution ledger.
clients/python Python client with the same keypair and voucher files as the TS client. Signatures verified byte-equal.
clients/curl The whole protocol in a bash script: curl, jq and one signing call.
examples/search-proxy A gated search API with a live dashboard for demos.
examples/site-review A job marketplace: agents pay for one API with any listed job (website QA review, labelling, invoice extraction), and posters add new jobs as JSON. Page at /market.
use-cases/ 9 runnable stories: dataset builder, x402 side by side, rate-limit upgrade, MCP agent, multi-seller wallet, trust tiers, paid crawl, marketplace, triple gate.
bench/ Simulated agents against hidden ground truth. Produces the 6 go/no-go numbers.

Quick start#

sh
pnpm install
pnpm build
pnpm test          # unit + e2e
pnpm bench         # prints the metrics table, writes bench/out/report.md
pnpm example       # gated search API on :8787, dashboard at /dashboard?token=demo
pnpm --workspace-concurrency=1 --filter 'd402-uc-*' run start   # all 9 use cases
bash clients/curl/walkthrough.sh                                 # the protocol in curl
cd clients/python && python3 -m unittest                         # Python client tests

A fresh pnpm install prints 7 "Failed to create bin" warnings because dist/ does not exist yet. The warnings are harmless; run pnpm build then pnpm install again to get the workspace bins, or run them as node packages//dist/cli.js (dist/bin.js for @d402-labs/mcp).

Run pnpm test for the current count; CI runs it on Node 22 and 24 plus the Python suite.

Packages are not published yet; the release workflow is ready (see Publishing). Run the bins from the repo after pnpm build, as in the commands below, or pnpm link them.

Warning: an unrelated package named d402 exists on npm (v0.4.1, github.com/programmaman/d402), so npx d402 runs a stranger's code. Our agent CLI is called d402-agent for that reason. From the repo, run it as node packages/client/dist/cli.js.

Seller side, 10 lines:

ts
import { Hono } from "hono";
import { createD402 } from "@d402-labs/server";

const d = createD402({
  sellerId: "api.example.com",
  taskUrl: "https://api.example.com/.well-known/d402/tasks",
  scope: ["/search"],
  secret: process.env.D402_SECRET!,
  labels: ["sports", "business", "tech", "world"],
  tiers: [{ id: "s", items: 5, est_tokens: 1000, reward: { calls: 10 } }],
});
d.tasks.loadFile("tasks.jsonl");

const app = new Hono();
app.route("/", d.routes);
app.use("/search", d.gate);
app.get("/search", (c) => c.json({ hits: [] }));

Agent side, 5 lines:

ts
import { createD402Client, loadOrCreateKeypair, createLlmSolver } from "@d402-labs/client";

const client = createD402Client({
  keypair: loadOrCreateKeypair("~/.d402/keypair.json"),
  solver: createLlmSolver({ complete: (prompt) => myModel(prompt) }),
});
const res = await client.fetch("https://api.example.com/search?q=rates");

Three ways in#

All commands run from the repo root after pnpm build.

Seller with an existing API and no time:

sh
node packages/proxy/dist/cli.js --upstream https://api.example.com --tasks tickets.jsonl --scope /v1 --admin-token demo

Seller who wants to be an MCP connector (tools paid in labelled data, same vouchers as the HTTP routes):

sh
node packages/mcp-seller/dist/cli.js --tasks tickets.jsonl --labels a,b,c --scope /mcp --port 8788 --secret $D402_SECRET

Agent in Claude Code or Claude Desktop:

sh
claude mcp add d402 -e D402_HOME=~/.d402 -- node "$PWD/packages/mcp/dist/bin.js"

Site with no data of its own (labelling work leased from a pool, labels go back to the vendor who posted it):

sh
node packages/proxy/dist/cli.js --upstream https://api.example.com --pool-url https://pool.example.com --site-key $SITE_KEY

Seller who also wants money: --x402-pay-to 0x... --mpp-tempo-recipient 0x... on d402-proxy, or schemes: [createX402Scheme(...), createMppScheme(...)] in code.

sh
node packages/proxy/dist/cli.js --upstream https://api.example.com --tasks tickets.jsonl --scope /v1 \
  --x402-pay-to 0xYourAddress --mpp-tempo-recipient 0xYourAddress

Human at a terminal (d402-agent here is alias d402-agent="node $PWD/packages/client/dist/cli.js"):

sh
d402-agent bundle https://api.example.com --tier s          # prints the bundle: bundleId, labels, items
# label every item into answers.json: {"<itemId>": "<label>", ...}
d402-agent submit <bundleId> --answers answers.json          # signs, submits, stores the voucher
d402-agent fetch "https://api.example.com/v1/search?q=rates" # spends it

d402-agent earn --answers key.json does all three steps in one go, but only with an answer key that covers every item it might be given; it is for demos and tests.

Once the packages are published, the same commands become npx -p @d402-labs/proxy d402-proxy ..., npx -p @d402-labs/mcp-seller d402-mcp-seller ..., npx -p @d402-labs/client d402-agent ... and claude mcp add d402 -- d402-mcp (after npm i -g @d402-labs/mcp). Name the package with -p: a bare npx d402-proxy looks up an unscoped package called d402-proxy on npm, which is not ours.

One 402, three ways to pay#

With @d402-labs/x402 and @d402-labs/mpp added as schemes, one gated route answers one 402 that a labelling agent, a USDC wallet and an MPP client can each read. The body is d402's offer with x402's exact entry appended, and the MPP challenge is a header:

HTTP/1.1 402 Payment Required
WWW-Authenticate: Payment id="...", realm="api.example.com", method="tempo", intent="charge", request="..."
Content-Type: application/json

{ "d402": "1", "x402Version": 1,
  "accepts": [
    { "scheme": "d402", "sellerId": "api.example.com", "taskUrl": "...", "scope": ["/v1"], "tiers": [ ... ], "hint": "..." },
    { "scheme": "exact", "network": "base-sepolia", "maxAmountRequired": "7000", "asset": "<USDC>", "payTo": "0x...", "resource": "..." },
    { "scheme": "mpp", "challenge": "WWW-Authenticate", "methods": ["tempo/charge"], "amount": "0.007", "currency": "USD" }
  ] }

The agent comes back with D402-Voucher (labels), X-PAYMENT (x402) or Authorization: Payment ... (MPP). Use case 09 runs all three. Settlement was verified with injected facilitators; real USDC and card settlement need a laptop with network and a testnet wallet, steps in packages/x402/README.md and packages/mpp/README.md.

The 6 numbers#

The bench measures what decides whether the medium holds:

Number Bar
Resolved-label accuracy vs ground truth >= 90%, and above any single agent
Golden pass rate for honest agents > 85%
Bundles until an item resolves < 4
Tokens per call earned < 200
Seconds added per gated request, cached voucher < 0.5s
Bundles before a lazy agent is cut off <= 5 (the spec floor; it earns 0 calls either way)

Bench results#

One run of pnpm bench (2,000 items, 15% golden, 7 simulated agents, 60 rounds each, agents seeded with 42). Full report with the per-agent table in bench/REPORT.md.

Only the simulated agents are seeded; golden sampling is random, so counts vary a little between runs. Every run must pass every bar.

Both runs pass every bar. Read the caveats in the report: the bench raises the rate limits so 60 rounds fit in 5 seconds, and simulated agents err independently, which real models on the same family may not.

Status#

v1. One task type (classify). Bearer vouchers by default; bindVouchers: true ties spends to the agent's Ed25519 key and requireSpendNonce: true closes replay inside the clock skew (spec 7.2). Turn it on with --bind-vouchers --require-spend-nonce on d402-proxy and d402-mcp-seller, or D402_BIND_VOUCHERS=1 D402_REQUIRE_SPEND_NONCE=1 on the example. Key and IP rate limits are the only Sybil defence. See spec/SPEC.md section 11.

Publishing#

Nothing is on npm yet. .github/workflows/release.yml publishes the 9 packages under packages/ (spec, server, client, mcp, mcp-seller, proxy, x402, mpp, pool) at the versions in their package.json. pnpm publish rewrites workspace:* dependencies to the real version in each tarball.

Before the first run:

  1. The packages publish under the @d402-labs npm scope (the bare @d402 scope belongs to the author of an unrelated d402 package). Create the d402-labs org on npmjs.com and make sure the publishing account owns it.
  2. Add an npm automation token with publish rights on the scope as the repository secret NPM_TOKEN.
  3. Run the workflow (Actions, release, Run workflow) with dry_run left on. It installs, builds, tests and runs pnpm publish --dry-run, which prints every tarball's contents.
  4. Run it again with dry_run off and tag set to the version, e.g. v0.1.0. It publishes with npm provenance and creates a GitHub release for the tag.

Locally, pnpm build && pnpm -r --filter './packages/**' publish --dry-run --no-git-checks does the same dry run.
