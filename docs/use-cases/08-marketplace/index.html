use case / 08-marketplace

08 marketplace

A vendor posts 300 support tickets (45 golden) to a d402 pool. Two sites, a weather API and a quotes API, have no data of their own to gate with, so each boots its d402 server from its first lease (the pool's labels and instructions) and runs createPoolSync: lease more when low, push votes with agent keys hashed, mark what the pool resolved. Two agents per site, four model families, label until their site has nothing new; the sites sync after every round. The pool applies the SPEC 5.3 resolution rule across both sites, so an item needs three agreeing agents and those never all sit on one site here. The vendor exports the resolved labels over GET /v1/batches/:id/export, and the pool's ledger (GET /v1/sites) says what each site contributed. No money moves; the ledger is what a revenue share would be computed from.

sh
pnpm --filter d402-uc-marketplace run start

What one run printed (abridged; your counts will differ, around 210 to 240 of 255 resolved):

1. pool up at http://127.0.0.1:40397; vendor "Acme Support" posted batch b_Tu5m...: 300 tickets, 45 golden, labels low/medium/high/critical
2. two sites with no data of their own gate /v1 with pool work:
   weather.example  up at http://127.0.0.1:45209: own items 0, first lease 120 (30 golden), labels from the pool, agents claude (p=0.95) + gpt (p=0.93)
   quotes.example   up at http://127.0.0.1:46007: own items 0, first lease 120 (30 golden), labels from the pool, agents gemini (p=0.96) + llama (p=0.94)
3. agents label, sites sync with the pool after every round:
   round  1: 348 votes pushed, 201 items leased, pool resolved 83/255
   round  2: 320 votes pushed, 159 items leased, pool resolved 159/255
   round  3: 284 votes pushed,   0 items leased, pool resolved 232/255
   round  4:   0 votes pushed,   0 items leased, pool resolved 232/255
4. vendor exports resolved labels with GET /v1/batches/b_Tu5m.../export:
   232 of 255 tickets resolved (23 still open: every agent has seen them, they need a 5th opinion), accuracy vs hidden truth 232/232 = 100.0%
   t_0002 critical w=2.00 voters=4 sites=2  "The whole 400-seat enterprise account has been hit by a login loop that locks out every single user."
5. the pool's contribution ledger (what a revenue share would be computed from):
   weather.example  leased 300, pushed 474 votes, 40 bundles passed, contributed to 232 resolved items; agents claude 20/20 bundles -> GET 200, gpt 20/23 bundles -> GET 200
   quotes.example   leased 300, pushed 478 votes, 38 bundles passed, contributed to 232 resolved items; agents gemini 18/20 bundles -> GET 200, llama 20/20 bundles -> GET 200

RESULT: 232/255 tickets labelled at 100.0% by 4 agents on 2 sites that had no data of their own; ledger: weather.example 232 items / 40 bundles, quotes.example 232 items / 38 bundles; no money moved

The exact counts vary a little between runs: expect around 210 to 240 of 255 resolved. The pool samples goldens at random for each lease, so which bundles fail the quality bar (and lose their votes) is not fixed. The open tickets have been seen by all four agents and need a fifth opinion; a third site, or a stronger agent, would close them.
