09 triple gate: one 402, three ways to pay

A quote API wants to be paid and does not care how. Its single GET /quote takes a d402 voucher (labels), an x402 payment (USDC on Base via Coinbase's protocol) or an MPP credential (Stripe/Tempo's Machine Payments Protocol), and when it gets none of them it answers one 402 that offers all three. The x402 and MPP parts are the real SDKs (x402-hono/x402-fetch/x402 v1 from Coinbase, mppx from Tempo/Stripe), wired for real; what cannot run without network (facilitator settlement, Tempo broadcast) is injectable and is injected in the tests.

sh
pnpm --filter d402-uc-triple-gate run start                      # the story, no network, ~4 s
TRIPLE_GATE_MOCK=1 pnpm --filter d402-uc-triple-gate run start   # same, with x402 + MPP verification injected: all three reach 200
pnpm exec vitest run use-cases/09-triple-gate                    # 22 tests, no network

x402 (USDC) MPP (Tempo / Stripe) d402 (labels)
where in the 402 body.accepts[scheme=exact] + body.x402Version WWW-Authenticate: Payment … body.accepts[scheme=d402]
how to pay X-PAYMENT: Authorization: Payment D402-Voucher:
who checks it facilitator POST /verify then /settle (x402/verify) mppx server handler (verifies, broadcasts on Tempo) d402.spend()
proof on the 200 X-PAYMENT-RESPONSE (settlement, base64 JSON) Payment-Receipt (base64url JSON) D402-Calls-Remaining

Precedence inside the gate is voucher, then X-PAYMENT, then Authorization: Payment; a request carrying both a voucher and an x402 header is served from the voucher and the facilitator is never called.

The story#

1. seller up at http://127.0.0.1:42789; GET /quote -> HTTP 402. This one response offers USDC, card/stablecoin via MPP, and labels:
   WWW-Authenticate: Payment id="vknOku5_…", realm="quotes.example", method="tempo", intent="char...      <- MPP (mppx), methods [tempo]
   body.x402Version: 1, body.accepts[].scheme: [d402, exact]
     d402  -> label 5 items for 10 calls (seller quotes.example)      <- labels (@d402-labs/client)
     exact -> 0.007 USDC on base-sepolia to 0x7F3c0A9e...             <- x402 (x402-fetch / x402/client)
     mpp   -> tempo/charge 7000 base units of 0x20c000...6874BE on chain 42431
     mpp   -> tempo/charge 7000 base units of 0x20c000...000000 on chain 42431
2. agent A (labels): 402 -> labelled 1 bundle of 5 snippets -> HTTP 200 in 55 ms, D402-Calls-Remaining: 9
3. agent B (USDC): would pay scheme "exact": 0.007 USDC (7000 base units) on base-sepolia to 0x7F3c…, asset 0x036C…
   set X402_PRIVATE_KEY with Base Sepolia USDC to settle for real (facilitator https://x402.org/facilitator)
4. agent C (MPP): parsed the WWW-Authenticate: Payment challenge with mppx: 2 offer(s): tempo/charge 7000 …
   set MPP_PRIVATE_KEY (a funded Tempo testnet key, `mppx account create`) to pay for real; STRIPE_SECRET_KEY adds the card method
5. side by side: …

RESULT: one 402, three ways to pay: USDC (x402), card/stablecoin (MPP), labels (d402); paid here with labels

With TRIPLE_GATE_MOCK=1 agents B and C pay too: B signs a real X-PAYMENT with a throwaway viem key (x402's own createPaymentHeader, offline) and the gate's injected facilitator accepts it; C builds a credential with mppx's Credential.from from the served challenge and the injected MPP verifier accepts it. Both lines are labelled MOCK; nothing touches a chain.

What was verified here vs what needs the laptop#

Verified in this repo, no network (the 22 tests):

  • the 402 body parses with Offer from @d402-labs/spec and its exact entry parses with x402's PaymentRequirementsSchema, with the configured price ($0.007 -> 7000), network and checksummed payTo; x402Version: 1; WWW-Authenticate starts with Payment and mppx's Challenge.fromResponseList parses it back to tempo/charge, amount 7000, chain 42431.
  • d402: earn + spend -> 200, 9 calls left; a bad voucher -> merged 402 with error: "voucher_invalid" and all three offers intact.
  • x402: a real X-PAYMENT (signed with x402's client code) with verifyX402 / settleX402 injected -> 200 + X-PAYMENT-RESPONSE decodable by x402-fetch's decodeXPaymentResponse; injected failure -> 402 with error: "insufficient_funds"; malformed header -> 402 without calling verify; settle failure -> 402.
  • x402 with the real x402-hono paymentMiddleware + real x402-fetch wrapFetchWithPayment against a local fake facilitator (port 0, answers /verify and /settle) -> 200; and the triple gate with facilitatorUrl pointed at that fake, no injection -> x402/verify's useFacilitator calls /verify then /settle -> 200.
  • MPP: an Authorization: Payment … built with mppx's Credential from the served challenge, verifyMpp injected -> 200 + Payment-Receipt that Receipt.deserialize reads; injected failure -> 402 with the reason and a fresh challenge; malformed / Bearer -> 402 without calling verify.
  • precedence: voucher + X-PAYMENT -> voucher; X-PAYMENT + MPP -> x402.

Needs network (the laptop): the facilitator's real /verify + /settle on Base Sepolia, and mppx's Tempo broadcast / Stripe SPT. Nothing in the automated tests reaches them.

Format-compatible, not settled: when verifyMpp is injected, the Payment-Receipt is produced by mppx's Receipt.serialize with the credential's transaction hash as reference; a real run gets the receipt from mppx itself (withReceipt). Likewise the mock X-PAYMENT-RESPONSE is x402's settleResponseHeader over a fake transaction hash.

A finding about x402-fetch#

x402-fetch@1.2.0's wrapFetchWithPayment does accepts.map((x) => PaymentRequirementsSchema.parse(x)) on every entry and that schema is scheme: z.enum(["exact"]), so a d402 entry throws whatever its position in accepts (a test pins this). Moving d402 last does not help, so d402 stays first, as every other seller in this repo does. Agent B therefore uses src/x402-client.ts: the same flow as x402-fetch, built from x402's own selectPaymentRequirements and createPaymentHeader, with one extra line that keeps the exact entries. The server side has no such problem: x402-hono's 402 body is exactly { x402Version, accepts, error }, which is what the gate emits, and the X-PAYMENT header is decoded with x402/schemes' exact.evm.decodePayment, the function the middleware uses.

Run it for real on your laptop#

Everything below needs outbound network (x402.org, Base Sepolia RPC, Tempo RPC, Stripe); the container this was written in has none.

x402 on Base Sepolia (USDC)

  1. A key. Either cast wallet new (Foundry) or node -e "const {generatePrivateKey,privateKeyToAccount}=require('viem/accounts');const k=generatePrivateKey();console.log(k, privateKeyToAccount(k).address)" (run from this folder, where viem is installed).
  2. Testnet funds for that address: Base Sepolia ETH is not needed (EIP-3009 transfers are gasless for the payer; the facilitator pays gas), USDC is. Get Base Sepolia USDC from the Circle faucet (https://faucet.circle.com, pick Base Sepolia) or Coinbase's developer platform faucet. The asset is 0x036CbD53842c5426634e7929541eC2318f3dCF7e (what x402 itself puts in the offer). One quote costs 0.007 USDC.
  3. Run:
sh
export X402_PRIVATE_KEY=0x…                      # the payer (agent B); needs Base Sepolia USDC
export X402_PAY_TO=0x…                            # your receiving address (default: a demo address)
# export X402_FACILITATOR_URL=https://x402.org/facilitator   # the default; it settles base-sepolia for free
pnpm --filter d402-uc-triple-gate run start

Agent B then signs the EIP-3009 authorization with x402/client, the gate calls the facilitator's /verify and, after serving the quote, /settle; the 200 carries X-PAYMENT-RESPONSE with the Base Sepolia transaction hash (decodeXPaymentResponse prints it). Check it on https://sepolia.basescan.org.

MPP on Tempo testnet (stablecoin), optionally Stripe (card)

  1. An account: npx mppx account create (stored in the OS keychain, auto-funded on Tempo testnet; mppx account fund --account main --network testnet tops it up). mppx reads MPPX_PRIVATE_KEY as an alternative to the keychain; to feed the story export the key as MPP_PRIVATE_KEY (mppx account export or generate one with viem and fund it with mppx account fund).
  2. Run:
sh
export MPP_PRIVATE_KEY=0x…                        # the payer (agent C), funded on Tempo testnet (chain 42431)
export MPP_RECIPIENT=0x…                          # your receiving address (default: the demo address)
export MPP_SECRET_KEY="$(openssl rand -base64 32)"   # HMAC for challenge ids (a dev default is used if unset)
pnpm --filter d402-uc-triple-gate run start

Agent C then uses mppx/client (Mppx.create({ methods: [tempo({ account })], polyfill: false }).fetch), which reads the WWW-Authenticate: Payment challenge, pays on Tempo testnet and retries with Authorization: Payment …; the gate's mppx server handler verifies the transaction and the 200 carries Payment-Receipt.

The mppx CLI can also drive the gate directly, which is a good booth demo: npx mppx http://127.0.0.1:/quote?symbol=ACME pays via MPP, and npx mppx … --protocol x402 pays the same 402 via x402 (mppx ships an x402 client too and its --protocol auto prefers MPP when both are offered). For that, run the story with TRIPLE_GATE_HOLD=1: it keeps the seller listening after the RESULT line and prints the URL to point mppx at.

Card via Stripe: mppx's Stripe method (stripe.spt({ secretKey, networkId, currency: "usd", decimals: 2, paymentMethodTypes: ["card"] })) is wired in when STRIPE_SECRET_KEY (an sk_test_… key) is set; it also needs STRIPE_PROFILE_ID (the machine-payments profile id mppx calls networkId). The 402 then carries a second WWW-Authenticate challenge with method="stripe". This path is typechecked against the SDK but was not run here (no network).

Environment variables#

var used by default
X402_PAY_TO gate: x402 payTo demo address 0x7f3c…293a
X402_FACILITATOR_URL gate: x402/verify useFacilitator https://x402.org/facilitator
X402_PRIVATE_KEY agent B: pays for real unset -> prints what it would pay
MPP_RECIPIENT gate: tempo({ recipient }) demo address
MPP_SECRET_KEY gate: Mppx.create({ secretKey }) a dev-only constant
MPP_PRIVATE_KEY agent C: pays for real with mppx/client unset -> prints the parsed challenge
STRIPE_SECRET_KEY, STRIPE_PROFILE_ID gate: adds stripe.spt to the MPP methods unset -> Tempo only
TRIPLE_GATE_MOCK=1 story: inject accepting verifiers for x402 and MPP off
TRIPLE_GATE_HOLD=1 story: keep the seller listening after the RESULT (for npx mppx demos) off

SDK facts this is built on (read from the installed packages)#

  • x402-hono@1.2.0: paymentMiddleware(payTo, routes, facilitator?, paywall?); routes = { "GET /quote": { price: "$0.007", network: "base-sepolia" } }; facilitator = { url, createAuthHeaders? }, default https://x402.org/facilitator. Reads X-PAYMENT; 402 body { error, accepts: PaymentRequirements[], x402Version: 1 }; on success sets X-PAYMENT-RESPONSE. The package is marked deprecated in favour of @x402/hono@2 (whose 402 moves to a PAYMENT-REQUIRED header and PAYMENT-SIGNATURE request header); v1 was chosen for the JSON body shape.
  • x402-fetch@1.2.0: wrapFetchWithPayment(fetch, signer, maxValue = 100000n, selector?, config?), plus createSigner(network, privateKey) and decodeXPaymentResponse(header).
  • x402@1.2.0: x402/types (PaymentRequirementsSchema, settleResponseHeader), x402/shared (processPriceToAtomicAmount, findMatchingPaymentRequirements), x402/client (createPaymentHeader, selectPaymentRequirements), x402/schemes (exact.evm.decodePayment), x402/verify (useFacilitator({ url }) -> { verify, settle }, which POSTs { x402Version, paymentPayload, paymentRequirements } to ${url}/verify and /settle).
  • mppx@0.13.5: server Mppx.create({ methods: [tempo({ recipient, testnet, store })], secretKey, realm }), mppx.charge({ amount })(request) -> { status: 402, challenge: Response } | { status: 200, withReceipt(res) }, mppx.compose([...]) for several methods, stripe.spt({ secretKey | client, networkId, currency, decimals, paymentMethodTypes }); challenge header Payment id=…, realm=…, method=…, intent=…, request=, expires=…, opaque=…; credential header Authorization: Payment (Payment-Authorization with requiresAuth); receipt header Payment-Receipt: ; client Mppx.create({ methods: [tempo({ account })], polyfill, fetch }).fetch; CLI mppx account create|fund|export, mppx [--protocol mpp|x402].

Settle one real USDC payment in two commands#

sh
pnpm --filter d402-uc-triple-gate run settle:x402          # prints the agent address to fund
# fund it with Base Sepolia USDC at https://faucet.circle.com (no ETH needed; the facilitator pays gas)
pnpm --filter d402-uc-triple-gate run settle:x402 -- --pay # pays 0.007 USDC through https://x402.org/facilitator, prints the tx link

The key is saved at $D402_HOME/x402-agent.json (default ~/.d402). Set X402_PAY_TO to your seller wallet, otherwise the demo pays a burn address. Needs a network route to x402.org.
